# Homunculus tome review

**Review date:** 2026-07-24  
**Mode:** THE BINDER — REVIEW  
**Scope:** `tomes/homunculus/`  
**Primary standards:** `course-configuration-guide.md`, `course-improvement-guide.md`  
**Supporting references consulted:** the relevant chapter, duel-bank, and external-workspace rules in `tome-authoring/3-chapters.md`, `tome-authoring/4-duel-bank.md`, and `tome-authoring/5-runtimes.md`

## Recommendation and implementation order

The tome’s arc, voice, readings, rubrics, feedback, and challenge depth are strong, and both validators report **0 errors and 0 warnings**; that clean mechanical result does not reduce the substantive work. The urgent priorities are to protect private learner data at the external-grading boundary, stop lessons from supplying the canonical files their Workings assess, move duel and intrusion challenges behind the lessons that teach them, and repair contradictory QLoRA math, quantization reasoning, and memory gates. The next tier is to align Working requirements with taught and observable proof, correct rebuild/template invariants, and replace the later course’s highly predictable exercise grid with balanced answers and production-shaped cumulative practice. Finish by improving interleaving, terminology and durable-total wording, lesson-layout variety and length, contradictory retrieval/memory examples, and safe repository hygiene without renaming progress-keyed legacy IDs.

Implement the work in this dependency-aware order:

1. Define and test a privacy-safe external-workspace grading boundary, including a small sanitized evidence surface and explicit learner disclosure.
2. Correct LoRA/QLoRA shapes, arithmetic, NF4-versus-GGUF reasoning, adapter-state accounting, and every downstream prompt, feedback item, challenge, and Working that repeats those claims.
3. Restore the single configured 2 GiB memory gate and correct rebuild, template, determinism, retrieval-window, and memory-prose contradictions across all surfaces.
4. Audit duel and intrusion prerequisites against their actual unlock points, rewrite or re-tier premature challenges, regenerate attacks from `attacks_src.toml`, and revalidate.
5. Remove canonical project answers from learner-visible lessons and rebuild each Working’s requirement-to-teaching-to-proof alignment.
6. Break the fixed later-course exercise grid, rebalance MC answer indices, and add targeted interleaving and production-shaped diagnosis practice.
7. Correct terminology, cross-references, fixed-total wording, layout variety, lesson-length outliers, and unsupported word-count metadata.
8. Remove only verified-empty orphan directories, document the legacy badge-ID exception, and preserve all existing progress-keyed IDs.

## Findings, highest priority first

### 1. Critical — the grading boundary conflicts with the course’s privacy promise

`tome.toml` sets `externalWorkspace = true`, while the project explicitly stores personal Notion exports, curated personal completions, evaluation prompts, adapters, reports, and a full llama.cpp checkout in the chosen workspace. The external-workspace authoring contract says grading collects up to 400 workspace files and skips only a fixed set of directories plus any tome-defined `runtime.excludeDirs`. Homunculus defines no exclusions.

Consequences:

- `data/raw/notion/`, `data/drafts.jsonl`, and `data/curated/*.jsonl` can contain the learner’s private writing, third-party material, or secrets that escaped triage. Section IV’s Working explicitly asks for those artifacts in the graded workspace.
- The promise in `[meta].description` and `[narrative].objective` is a private local assistant, but the tome never tells the learner that grading may disclose workspace content to the configured AI grader.
- `vendor/llama.cpp/` alone can exceed the 400-file collection cap. It can crowd out the learner’s own `src/`, `tests/`, manifests, and reports, producing incomplete or unstable grading evidence.
- Large derived trees under `artifacts/` and `rebuilds/` compound the collection problem even where binary files are skipped.

**Remediation:** establish an explicit privacy-safe grading surface before any content rewrite. Add narrowly chosen `runtime.excludeDirs` for bulky and sensitive trees such as `vendor`, raw/private data, model weights, and clean-rebuild outputs. Move or copy only sanitized, hash-based evidence needed for grading into a small declared evidence surface (for example, selected source, tests, manifests, and redacted reports). Rewrite Working requirements and rubrics so the grader never needs raw personal notes or completions. Tell the learner plainly what is and is not transmitted for grading. Verify that the grader receives all required evidence within the 400-file cap.

### 2. Critical — learner-visible lessons prebuild the canonical Working

The improvement and authoring guides are explicit: the Working is where the learner constructs the project; learner-visible examples must not already implement canonical project requirements.

Homunculus repeatedly crosses that line:

- `sections/s01/lessons/l04.toml` gives a complete `src/homunculus/doctor.py` plus `tests/test_doctor.py`; the Section I Working grades those exact files.
- `sections/s02/lessons/l05.toml` gives nearly the entire `src/homunculus/baseline.py`; the Section II Working grades that module and its report.
- `sections/s04/lessons/l05.toml` gives a large, nearly complete `src/homunculus/curate.py`; the Section IV Working grades that file and its derived corpus.
- `sections/s05/lessons/l02.toml`, `l03.toml`, and `l05.toml` combine into most of `src/homunculus/train.py`; the Section V Working asks the learner to submit that trainer.
- Later lessons provide core canonical functions for `evaluate.py`, `merge.py`, and `assistant.py`, even when the complete file is not shown.

The later Workings remain broad, but much of the most important implementation becomes copying, joining snippets, and filling omitted glue. That is weaker evidence than the detailed rubrics imply.

**Remediation:** keep the project specifications, constraints, commands, diagnostics, and acceptance checks, but replace canonical implementations with small disposable examples using different filenames, identifiers, data, and problem shapes. For example, teach path-safe loading on a toy fixture rather than supplying `policy.py`; teach a one-case HTTP recorder rather than the project’s `baseline.py`; teach trainer construction on a disposable dataset without assembling the production CLI. Preserve complete project answers only in an authorized hidden proof/reference surface, not in lesson bodies or visible exercise solutions.

### 3. Critical — challenge banks test material before it is taught

The duel-bank contract states that tier N unlocks after N sections. Several `attacks_src.toml` entries violate the “first use must be an introduction” and “no untaught dependency” rules:

- Tier 1 includes **THE BASELINE PROMPTS**, taught in Section II, and **THE MAP READ ALOUD**, which uses adapter rank before the memory/LoRA sections.
- Tier 4 includes **THE ONE-STEP WITNESS**, **THE ADAPTER SEAM**, and **THE PARAMETER COUNT**, all taught in Section V.
- All five tier-5 RAG/vector/chunk challenges depend on Section VII.
- All five tier-6 merge, quantization, Ollama, served-regression, or rebuild challenges depend on Sections IX–X.

The intrusion bank has the same defect on a smaller scale:

- Min 1 **THE MEMORY THIEF** depends on Section III.
- Min 7 **THE POLICY HASH** depends on Section VIII.
- Min 9 **THE FRESH REBUILD** depends on Section X.

At least half of the 30 duel challenges and three of the 25 intrusion challenges are premature.

**Remediation:** audit every challenge against its actual unlock point. Re-tier where the mechanic permits it, or rewrite premature entries at the same tier to practice already-taught capabilities while preserving bank depth. Keep at least five duel challenges per tier. After changing `attacks_src.toml`, regenerate `generated/attacks.toml` with the trusted generator and revalidate; never edit the generated file directly.

### 4. Critical — Section V’s core QLoRA math is internally inconsistent

Several errors occur in `sections/s05/lessons/l01.toml` and propagate into feedback and challenges:

- The prose defines `A ∈ R^(d×r)` and `B ∈ R^(r×k)` while using `BAx`. Those shapes do not multiply in that order. The code block uses the conventional compatible shapes: `A = (rank, in_features)` and `B = (out_features, rank)`.
- Exercise `s05-l01-e2` says a 7B fp16 full fine-tune costs `14 GB + 14 GB + 28 GB = 56 GB`, while the course’s own 12-byte ledger requires two fp32 Adam moments totaling 56 GB by themselves: `14 + 14 + 28 + 28 = 84 GB`. Section III correctly teaches 12 bytes per parameter and 96 GB for 8B.
- Exercise `s05-l01-e4` says it targets query and value projections, but its feedback switches to four projections. Its nominal correct option says roughly 0.1–0.2%, while the lesson’s own four-square-matrix calculation gives 524,288 / 7B ≈ 0.0075%. The prompt, option, feedback, and arithmetic cannot all be true.
- The lesson borrows “~4.5 bits per weight” from the Q4_K_M GGUF discussion to describe the NF4 training base, despite `s03-l06` correctly warning that GGUF serving estimates and NF4 training footprints are different formats with different metadata/workspace costs.
- `s05-l04` claims rank 128 costs “~4 MB” and is “almost certainly” memorization for 200 records. Under its own four-module dimensions, adapter weights alone exceed that, and full trainable state is much larger; overfitting risk must be measured rather than declared from a parameter-per-example ratio.

Supporting challenge content repeats the confusion:

- Duel **THE FULL FINETUNE TOLL** multiplies a 4 GB quantized base by six, mixing a full-fine-tune multiplier with a quantized-inference starting point.
- Duel **THE QUANTIZATION COMPROMISE** presents Q4_K_M as exactly one quarter of F16, contradicting the tome’s own warning that K-quants and metadata make that only a rough sanity estimate.

**Remediation:** rewrite the LoRA derivation from one consistent convention (`A: r×d_in`, `B: d_out×r`, `ΔW = BA`), recalculate every example from named target-module shapes, and distinguish adapter weights from gradients/optimizer state. Keep NF4 and GGUF estimates in separate ledgers. Recheck every related prompt, answer, hint, `whyWrong`, `explain`, intrusion, duel, and Working line after the correction.

### 5. High — the assessment grid is extremely predictable

The later half of the tome violates the chapter guide’s anti-template rules:

- Every one of the **27 lessons in Sections VI–X** has exactly four exercises in exactly this order: `mc`, `text`, `fill`, `write`.
- MC answer indices are heavily biased: **49 of 74** correct answers use index 0.
- In Sections VII–X, **all 21 MC answers** use index 0. Across Sections VI–X, 26 of 27 do.
- Section V already trends the same way, with 9 of 12 MC answers at index 0.

A learner can infer the correct choice without understanding the material, and the repeated four-item rhythm reads as generated rather than deliberately paced.

**Remediation:** redistribute MC choices so indices 0–3 are comparable across the tome and within later sections. Vary exercise count, order, and type based on the lesson: use occasional type/fading sequences for first-use APIs, diagnosis exercises, cumulative write labs, and reasoned text prompts. Do not mechanically shuffle choices without updating `answer`, `whyWrong`, `explain`, and hints.

### 6. High — the configured 2 GiB memory gate drifts to 1 GiB in minigames

The durable configuration in `s03-l06`, the Section III Working, and the Section V Working requires **2 GiB** of measured headroom. Challenge content teaches different gates:

- Intrusion **THE HEADROOM WARD** requires only 1 GB.
- Intrusion **THE DRY STEP** passes anything below 15 GB on a 16 GB card, again leaving only 1 GB.
- Duel **THE HEADROOM PROOF** sets `required_gb = 1.0`.

This is precisely the kind of cross-surface inconsistency the improvement guide warns about.

**Remediation:** use the single configured 2 GiB gate everywhere, preferably by naming it as a project configuration value rather than duplicating unexplained literals. Recalculate expected output and regenerate duel output.

### 7. High — challenge content contradicts rebuild and template policy

Two challenge concepts teach the wrong invariant:

- Duel **THE REBUILD MANIFEST** requires the rebuilt adapter hash to equal the old adapter hash. Section X and its Working correctly state that GPU training may be nondeterministic and that a rebuilt learned artifact must pass the same behavioral gates rather than be byte-identical.
- Intrusion **THE NATIVE TEMPLATE** says to keep “only the FROM directive.” The Section IX Modelfile correctly also contains `PARAMETER` and `SYSTEM`; only a hand-written `TEMPLATE` is forbidden.
- Intrusion **THE FRESH REBUILD** uses an ambiguous `manifest_matches` boolean that can reinforce the byte-equality misconception.

**Remediation:** make deterministic artifacts/hash inputs match, but judge learned adapters by lineage plus behavioral gates. Rewrite the template challenge to assert “no TEMPLATE override” while retaining `FROM`, approved `SYSTEM`, and serving parameters.

### 8. High — Working requirements and supplied implementation do not always agree

The strongest example is Section I:

- The Working requires proof of the llama.cpp build, pinned imports, GPU compute, and live Ollama.
- The supplied `doctor.py` checks packages, GPU, and Ollama, but never checks llama.cpp.
- The Working says `reports/doctor.txt` must prove the chain, while the supplied code does not record the current working directory, imported Homunculus path, llama.cpp binary/commit, or several ownership details praised by its own field notes and xray.

Section IV has a similar gap:

- The Working requires source-group leakage prevention, baseline-prompt leakage detection, rejection reporting, and review evidence.
- The supplied `curate.py` checks exact normalized duplicate completions and a small regex list, but it does not enforce one split per source, compare baseline prompts, validate a SHA-256 shape/content relationship, or produce the rejection log its own field notes require.

These can be valid independent Working tasks only after the canonical-code problem is fixed and the missing boundaries are explicitly taught as transfer, not implied to exist in the shown script.

**Remediation:** maintain one requirement-to-teaching-to-proof matrix per Working. Ensure every required boundary is introduced before the Working and has an observable check. Avoid describing a visible sample as “the real diagnostic” or “exact” when it omits graded requirements.

### 9. Medium — interleaving is present only lightly

There are good backward links—for example, Section VII contrasts RAG with Section IV’s stable voice, one FAISS exercise reuses a memory ledger, and Section X revisits component ownership. Most exercises, however, test only the lesson immediately above them. The later 27-lesson fixed grid makes this especially visible: each write lab is a small local list/dict/counting transformation, not cumulative use of prior project contracts.

**Remediation:** add deliberate backward practice without testing future material. Examples: a Section VIII policy case that also validates Section VII source IDs; a Section IX quantization case that must preserve the Section VI regression gate and Section III headroom contract; a Section X planner that reasons across corpus, RAG, policy, and serving hashes. Prefer novel integration or diagnosis over changing constants in a toy dict.

### 10. Medium — lesson layout and sizing need a deliberate variety pass

Strength is consistent, but the presentation becomes formulaic:

- All 53 lessons include field notes, which is excellent, but **none** uses a body `<ul>` or `<ol>`.
- Later lessons overwhelmingly follow the same paragraph → code → paragraph → callout → field-notes shape.
- `s02-l01` and `s03-l01` each contain two callouts, exceeding the one-callout-per-lesson rule.
- A simple rendered-text count places `s04-l01`, `s05-l01`, and especially `s05-l04` above the 600-word target, while `s10-l02` and `s10-l03` fall just below 300.
- `s05-l01` and `s05-l04` contain undocumented `body_words` fields (`520` and `550`) that do not match straightforward visible-text counts and are not part of the documented lesson schema.

**Remediation:** vary layout with concise lists, compact decision tables expressed in allowed HTML, and shorter code-first explanations. Merge duplicate callouts. Bring outliers into the 300–600 range without padding. Remove unsupported word-count metadata and let the authored body be the source of truth.

### 11. Medium — terminology and cross-references drift

The tome uses “rite” for both a section and a lesson. That ambiguity produces concrete errors:

- `s05-l01` opens “The seventh rite begins…” inside Section V.
- The same lesson says “the fifth rite proved” a quantization fact, apparently referring to a lesson inside Section III even though section briefs consistently call whole sections rites.
- `s04-l03` says “The fourth rite taught” an Ollama/template concept from a different section/lesson numbering scheme.

The durable-total rule is also violated:

- `tome.toml` boot text says **“Ten rites lie ahead”**. This is the fixed course-total occurrence that Review mode must report. The later `{N}` boot line already provides the durable form.

There is also a small wording mismatch in the final Working: it promises grounding in “online style references,” while the implementation uses locally stored, provenance-backed snapshots of online sources rather than live web retrieval.

**Remediation:** reserve “rite” for the course’s section-level `opsLabel`, use “lesson” for lesson references, and name exact section/lesson titles or IDs where a backward reference matters. Replace the fixed total with “The rites ahead…” or rely on `{N}`. Change “online style references” to “locally indexed snapshots of cited online sources.”

### 12. Medium — a retrieval example contradicts the actual chunk contract

`s04-l03` uses the assistant completion “512 tokens balances retrieval precision…” as a model training example. Section VII later correctly establishes a 200-token window with 30-token overlap because all-MiniLM-L6-v2 has a 256-token limit and explicitly says 512 would be truncated.

Even though the earlier sentence is inside example data, learners are told that completions are truthful, useful examples. It plants the wrong project value before the correct rule appears.

**Remediation:** replace the completion with a non-project fact or with the eventual 200/30 contract. Search all visible examples, solutions, and challenge text for old 512-token language.

### 13. Medium — memory prose contains a direct self-contradiction

`s03-l01` says every formula is a floor, calls the estimate optimistic, warns that unmodeled overhead makes actual use worse, and then ends by saying “the exact byte count is always a little pessimistic in practice.” The last adjective reverses the entire warning.

The same lesson’s example uses 32 layers. The frozen Qwen3-8B model card currently lists 36 layers, 32 query heads, and 8 KV heads. The example can remain generic, but it should be labeled illustrative so learners do not use it as the frozen model’s budget.

**Remediation:** change “pessimistic” to “optimistic” and explicitly label generic architecture numbers. Prefer loading actual config values for the project’s final memory report.

### 14. Low — orphan directories and inherited naming irregularities add maintenance noise

`sections/s11/` and `sections/s12/` exist as empty directories but are absent from `[content].sections`. They do not affect validation, yet they suggest removed chapters and caused a naïve section walker to fail.

Freestyle badge IDs use `s01-badge` through `s10-badge`, whereas current authoring guidance prefers `badge-sNN`. This is nonfunctional legacy drift. Because IDs key progress, they must **not** be renamed during an ordinary maintenance pass.

**Remediation:** remove only the empty, unreferenced directories after confirming they contain no hidden harness artifacts. Document the badge-ID exception and keep existing IDs unchanged; use the current convention only for any future appended section.
