# Homunculus tome review

- **Review mode:** THE BINDER / REVIEW
- **Reviewed:** 2026-07-24
- **Scope:** `tomes/homunculus/`, the repository course-configuration and course-improvement guides, and the platform paths that determine external-workspace execution, file collection, and grading
- **Validation:** `validate_tome.py` reports **0 errors and 0 warnings**, both normally and with `--strict`
- **Overall disposition:** **Broad correction is required before this tome should be represented as a private, reproducible, evidence-backed local-assistant course.**

## Recommendation and implementation order

Homunculus has a strong premise, an unusually coherent project arc, a memorable voice, a cumulative external-workspace build, useful source-grouping and prompt-injection lessons, a healthy reading/field-note habit, full multiple-choice feedback, and mechanically sound themes, economy, rubrics, and generated attack-bank synchronization. The central toolchain is also more current than its specificity may initially suggest: the RX 9070 XT/gfx1201 ROCm path is plausible, and current TRL still supports the direct `quantization_config` argument used by the course. Both normal and strict validators are clean.

That clean validator result must not be interpreted as release readiness. The validator does not test what learner files leave the machine, whether a Working can be run, whether grading can observe the artifacts named in its rubric, whether privacy vetoes actually veto a pass, whether examples disclose the assessed solution, whether challenges unlock after their prerequisites, or whether the technical explanations agree with their own arithmetic. Those are the tome's most important failures.

The recommended work is a coordinated reauthoring/release effort, not a sequence of small compatibility-preserving patches. Its material workstreams are:

- close the learner-data boundary: stop the default remote transmission of private notes, references, prompts, retrieved passages, debug traces, and other workspace files; disclose and minimize any optional remote grading;
- replace prose-only/self-attested grading with privacy-safe, observable assessment evidence, fix the mismatch between collected file types and rubric artifacts, provide a real CAST entry point, and make critical privacy/correctness gates capable of preventing a pass;
- redesign examples, exercises, and Workings so the assessed implementation is not already visible for copying and learners get production-shaped practice before they must assemble the system;
- correct the LoRA arithmetic and shapes, quantization/training terminology, determinism claims, memory/headroom rules, model-verification commands, and contradictory challenge-bank canon, then propagate one authoritative rule set everywhere;
- retier or rewrite every duel and intrusion that can unlock before its taught prerequisite, regenerate derived banks, and revalidate them;
- establish immutable model, dataset, environment, and build identities before baseline generation or training rather than retrospectively in the final section;
- either narrow the advertised hardware/platform promise to the actually hard-coded RX 9070 XT/gfx1201/ROCm target, with explicit host RAM, disk, OS, and tool prerequisites, or generalize and test a documented support matrix;
- rebuild the exercise grid to eliminate answer-position and four-item-shape predictability, add cumulative retrieval and diagnosis, improve hints, and make later practice interleave earlier skills;
- reconcile Working requirements with their starter implementations, repair readings and layout outliers, remove fixed-total and terminology drift, clean obsolete empty directories when safe, and preserve stable IDs unless a deliberate release migration authorizes progress changes.

Because the course has no mastery table or deterministic proof contract, the broad repair should not be smuggled into an ordinary legacy Iterate/Update pass. Use a dedicated reauthoring release, a new tome/version, or an explicitly authorized progress reset. Progress safety should determine the migration mechanism—preserving section, lesson, badge, and exercise IDs where their meaning remains valid—not excuse unsafe grading, incorrect instruction, or invalid evidence.

Implement in this dependency-aware order:

1. **Contain learner data first.** Define the local/remote trust boundary, inventory every collected path, default grading to a local-only or sanitized-evidence route, add explicit informed opt-in for any remote provider, and exclude raw/private and bulky generated directories from collection. Do not test the current remote path with real learner material.
2. **Choose the assessment and release architecture.** Decide whether this becomes a new version/tome or an authorized reset; define deterministic public checks, protected assessment cases, guided hardware checks, and a minimal proof bundle. Make privacy and correctness gates true vetoes rather than rubric suggestions. Define which evidence may be retained and for how long.
3. **Make execution and evidence observable.** Add one stable project command/entry point, align RUN/CAST with it, collect the actual required extensions (`.toml`, `.jsonl`, and the extensionless `Modelfile`) or emit a sanitized evidence manifest, prevent the 400-file cap from hiding assessable code, and verify the exact payload seen by every grader.
4. **Freeze scope and identities.** State the supported GPU/architecture, OS, ROCm/container, host RAM, disk, Docker, Git, CMake, Python, and Ollama prerequisites at entry. Capture Ollama digests, Hugging Face revisions, container digests, dependency locks, dataset hashes, and evaluation-set hashes before their first use, and fail on drift.
5. **Repair the technical canon.** Correct the LoRA equations and parameter-count exercise, full-fine-tune memory arithmetic, NF4/Q4_K_M distinction, context-size example, determinism language, headroom rule, quantization estimates, rebuild semantics, Modelfile rule, and model-load verification. Use the corrected canon to update lessons, feedback, Workings, tests, duels, and intrusions together.
6. **Repair prerequisite ordering.** Retier or rewrite all premature duels and intrusions while retaining the minimum bank depth, regenerate `attacks.toml` through the trusted generator, and audit every challenge against the knowledge available at its earliest unlock.
7. **Reauthor instruction and practice.** Replace production-ready assessed solutions with disposable analogous examples; add a scaffolded path through packaging, file safety, hashing, subprocesses, HTTP, JSONL, testing, model APIs, FAISS, and failure diagnosis; and make every Working's supplied artifacts genuinely satisfy its own stated requirements without being the answer key.
8. **Rebuild the assessment grid.** Redistribute multiple-choice answers, vary lesson assessment shapes, add spaced and interleaved retrieval, use transfer/debugging tasks instead of repeated toy exact-output prompts, and make hints reveal a reasoning step rather than the answer.
9. **Finish consistency and release verification.** Repair the two broken readings, fixed “ten rites” copy, rite/lesson terminology, layout/callout and length outliers, undocumented body metadata, and empty `s11`/`s12` directories where safe. Then run normal and strict validation, regenerate derived assets, replay the entire public/private assessment matrix on a clean supported machine, inspect privacy payloads, and test migration/progress behavior before release.

## Critical findings

### C1. The default grader can transmit the course's private data to a remote provider

The tome promises a “private local assistant,” but its default configuration selects `claude-cli` with a remote Claude model. In an external workspace, the grader recursively collects matching files from the learner-selected project and sends their contents as “STUDENT CODE (entire workspace).” The course deliberately places sensitive or content-bearing files inside that same project:

- imported Notion Markdown under `data/raw/notion/`;
- reference Markdown under `data/references/`;
- prompts, policies, and outbox artifacts in Markdown;
- response, retrieval, evaluation, and debug artifacts in `.json`, `.md`, or `.txt`;
- potentially private example text embedded in source or tests.

The default collection extensions are `.py`, `.md`, `.txt`, and `.json`, and the tome defines no `excludeDirs`. The collector can gather up to 400 matching files. Consequently, a normal grading attempt may transmit precisely the notes and retrieved passages the learner was taught to keep local. The same breadth can fill the cap with raw notes or vendor references and crowd out files that actually demonstrate the learner's work.

This is a learner-privacy defect, not merely a documentation omission. The later rubric language about local processing cannot constrain what the platform has already collected and sent. The local grade cache also retains collected file content, so the course needs an explicit retention/deletion story even when no remote provider is used.

**Remediation:** Default to a local-only grader or a purpose-built, sanitized proof bundle. Explicitly exclude raw notes, references, caches, outputs, reports, model artifacts, and other private/bulky directories; use an allowlisted assessment snapshot if the platform can support one. Before any optional remote submission, show exactly which files and provider are involved and require informed opt-in. Redact or synthesize evidence so private note text and retrieved chunks are never needed. Define local cache retention and deletion. Add a release test that enumerates the actual collected paths and fails if private fixtures enter the payload.

### C2. The platform cannot observe or execute much of the evidence the Workings claim to assess

The tome is configured with `externalWorkspace=true` and `projectFile="pyproject.toml"`, but it has no `runCommand`, `buildCommand`, `entryFile`, `codeExt`, or exclusions. The Python runtime therefore attempts `python3 main.py`, while the course builds no root `main.py`. CAST is not a stable way to run the project learners are constructing.

The grading path is weaker than the Working language suggests:

- without a build command, the generic build check only parses Python syntax;
- the grader cannot itself run the learner's GPU, Docker, Ollama, training, merge, FAISS, or Notion-import workflow;
- legacy grading receives the collected files plus the learner-facing brief/rubric, so reports and claims can substitute for observed execution;
- the passing threshold is numeric, while “critical” privacy rules are prose inside rubrics rather than enforced vetoes;
- there is no mastery table or deterministic proof version to supply protected evidence.

Several rubric-critical artifacts are invisible under the default extension filter:

- `pyproject.toml` and `homunculus.toml`;
- JSONL baselines, datasets, and evaluation records;
- the extensionless `Modelfile`.

This means a learner can omit or falsify important runtime evidence and still present persuasive prose, while correct artifacts may not reach the grader at all. A score at or above the ordinary pass threshold can also override what the course describes as a privacy-critical failure.

**Remediation:** Define an executable assessment contract before editing individual rubrics. Provide a stable root command or explicit runtime command. Use deterministic checks for files, schemas, hashes, path containment, split leakage, policy behavior, and reproducible CPU-safe units; use guided/manual receipts for hardware-only steps; reserve protected cases for transfer and privacy bypasses. Collect the required file types or, preferably, generate a minimal signed/sanitized evidence manifest from them. Make privacy violations, missing identity evidence, leakage, and unsafe output hard pass vetoes. Confirm that the grader sees the exact evidence claimed by each criterion and cannot pass on self-authored reports alone.

### C3. The teaching sequence exposes many assessed implementations before learners build them

The authoring guidance requires Worked examples to be disposable and Workings to be the place where the project is constructed, not recopied. Homunculus frequently does the reverse:

- `s01/l04` supplies a nearly complete `doctor.py` and test immediately before the Working assesses `doctor.py`;
- `s02/l05` supplies most of `baseline.py`;
- `s03/l06` gives the exact `homunculus.toml` later requested;
- `s04/l05` gives a near-complete `curate.py`;
- `s05/l02` through `s05/l06` progressively disclose most of `train.py`;
- later lessons likewise expose core evaluation, merge, retrieval, policy, and assistant functions that their Workings assess.

The nominal independent labs do not compensate. Most `write` exercises are small dictionary, list, counting, arithmetic, or exact-print tasks. Meanwhile the Workings require packaging, `argparse`, `pathlib`, hash manifests, subprocesses, HTTP, JSONL, tests, path containment, model APIs, FAISS, and operational diagnosis. The declared prerequisite is only basic Python. Learners are therefore pushed toward either copying the visible canonical implementation or making a large unsupported leap.

This undermines valid evidence of learning even if the grader is repaired: successful submission may show transcription, not transfer.

**Remediation:** Treat the entire lesson/example/Working sequence as one redesign. Keep examples analogous but disposable—different paths, data, constraints, or miniature APIs—and remove the production answer from the lesson immediately preceding assessment. Introduce the required engineering techniques through scaffolded, production-shaped practice and debugging before they are combined. Give Workings starter interfaces, fixtures, and observable contracts rather than complete implementations. Add protected transfer cases that require adapting the learned pattern rather than reproducing a visible file.

## High findings

### H1. Core technical explanations and exercises contain contradictions or wrong arithmetic

The most consequential errors are in the fine-tuning and deployment spine:

1. `s05/l01` describes LoRA matrices as \(A:d\times r\) and \(B:r\times k\) while writing \(BAx\). Those stated shapes cannot multiply in that order. The later code uses the conventional compatible orientation, so prose and implementation disagree.
2. `s05-l01-e2` totals a 7B full fine-tune as 56 GB from “14 GB weights + 14 GB gradients + 28 GB optimizer.” With the course's own premise of two 4-byte Adam states, the optimizer contribution is 56 GB, yielding roughly 84 GB before activations. Section III elsewhere correctly uses 12 bytes per parameter and estimates 96 GB for 8B.
3. `s05-l01-e4` asks for the percentage of trainable parameters for query/value rank-16 adapters without specifying layer count. Its explanation then silently changes scope to all four Q/K/V/O projections in what appears to be one layer. The selected range cannot be derived from the prompt, and the statement that depth does not matter is false for a whole-model adapter count.
4. `s05/l04` asserts that rank 128 on 200 rows is “almost certainly memorization” and pairs it with an unsupported memory figure. Capacity and overfit risk should be measured against the actual modules, tokens, epochs, validation behavior, and parameter count rather than inferred from rank and row count alone.
5. `s04/l03` asks why the base was frozen at `q4_K_M`, conflating the serving quantization with the NF4 training load the course otherwise teaches.
6. The same lesson's example endorses 512-token chunks, while the RAG section correctly identifies the selected MiniLM encoder's 256-token limit and chooses roughly 200-token chunks with overlap.
7. `s03/l01` calls the same estimates “optimistic” and then “pessimistic.”
8. `s02/l04` and a duel present temperature zero as fully deterministic; `s06` later correctly notes that GPU kernels, batching, software, and model identity can still change output.
9. `s09/l02` uses `llama-cli -m MODEL --help` as artifact verification. A help invocation does not establish that the model can be loaded and inferred with.

The challenge banks amplify this drift: headroom alternates between the canonical 2 GiB and 1 GiB; a full-fine-tune estimate multiplies from a 4 GB quantized inference base; Q4_K_M is treated as exactly one-quarter of F16 despite overhead; a rebuilt adapter is expected to reproduce a byte-identical hash despite the course teaching behavioral gates for nondeterministic training; and an intrusion says a valid `Modelfile` should retain only `FROM`, contradicting the course's correct use of `FROM`, `PARAMETER`, and `SYSTEM` while forbidding an inappropriate `TEMPLATE`.

Current upstream llama.cpp documentation also demonstrates why Q4_K_M should not be taught as a universal fixed “4.5 bits” conversion: its published Llama 3.1 8B example reports about 4.8944 bits per weight, and quantization recipes are tensor- and architecture-dependent. The course may use a planning approximation, but must label and test it as one. See the [llama.cpp quantization documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md).

**Remediation:** Create a single reviewed technical canon with dimensions, units, assumptions, and authoritative formulas. Derive the parameter-count exercise from explicit layer/module counts; use the course's own 12-byte optimizer-state model consistently; distinguish NF4 training loads from GGUF serving artifacts; make context sizes compatible with the selected embedding model; qualify determinism; and replace help-text verification with a small actual load/inference smoke test. Recalculate every dependent exercise, test, feedback block, rubric, duel, and intrusion rather than patching the lesson prose alone.

### H2. Fifteen duels and at least two intrusions can appear before their prerequisites

Duel tier \(N\) unlocks after \(N\) sections have passed, not after section \(N\)'s content has been taught. At least half of this bank is premature:

- **Tier 1:** `THE BASELINE PROMPTS` requires the section II baseline; `THE MAP READ ALOUD` depends on later memory-map/rank material.
- **Tier 4:** `THE ONE-STEP WITNESS`, `THE ADAPTER SEAM`, and `THE PARAMETER COUNT` depend on section V.
- **Tier 5:** all five RAG challenges depend on section VII.
- **Tier 6:** all five challenges about serving, merge/quantization, and rebuild behavior depend on sections IX or X.

Intrusions use their minimum-passed-section value in the same earliest-availability sense. `THE POLICY HASH` is marked for seven passed sections but depends on section VIII; `THE FRESH REBUILD` is marked for nine but depends on section X. Other challenges should be audited after the technical canon is fixed because rewriting may change their prerequisite.

This is not harmless previewing. The challenges are framed as assessment and progression, but can require vocabulary, formulas, file contracts, or operational rules the learner has never encountered.

**Remediation:** Build a prerequisite matrix for every challenge against its earliest unlock. Retier challenges whose concepts are sound; rewrite those that cannot fit the available six duel tiers; and replace late-only material with cumulative challenges using already taught concepts. Preserve at least five challenges per tier and adequate intrusion-pool depth. Regenerate `attacks.toml` from `attacks_src.toml` with the trusted generator and re-run validation rather than editing the generated bank directly.

### H3. Reproducibility identity is recorded after it is needed and remains incomplete

The course creates its baseline with the mutable Ollama name `qwen3:8b` and trains from `Qwen/Qwen3-8B` without a resolved Hugging Face revision. Early manifests record names and options, but not the immutable model content that produced the baseline, tokenizer behavior, adapter, or evaluation. Section X finally discusses resolved revisions and Ollama digests after all those artifacts have already been created.

Direct package versions in `pyproject.toml` are useful, but they are not a transitive lock and do not justify the broader “pinned toolchain” promise. Container image tags likewise need resolved image identity if they are meant to prove a rebuild. A later hash of a newly resolved model cannot establish what was actually used earlier.

**Remediation:** Resolve and record the Ollama model digest before the first baseline call; pin the Hugging Face commit before tokenizer/model load; bind dataset, split, prompt, environment, container, adapter, merged model, quantized model, and evaluation evidence to those identities. Add a lock or captured installed environment with hashes, record container digests, and make commands fail on identity mismatch. Teach this in the first relevant workflow rather than as a retrospective final-section improvement.

### H4. The advertised “16 GB AMD GPU” scope is broader than the implementation

The public description implies a general 16 GB AMD GPU course. The actual setup hard-codes an RX 9070 XT, gfx1201 wheels, a specific ROCm container line, and an Ubuntu-like workflow. Other 16 GB AMD GPUs can have different architecture, driver, wheel, kernel, and container compatibility. Host RAM and disk requirements become especially important during model conversion and quantization, yet are disclosed late and not quantified at entry.

The selected target itself is plausible: AMD's current compatibility material includes the RX 9070 XT, and bitsandbytes publishes preview gfx1201 ROCm wheels. The defect is the promise-to-implementation mismatch, not the choice of target. See AMD's [current Radeon compatibility matrix](https://rocm.docs.amd.com/projects/radeon/en/latest/docs/compatibility/compatibilityrad/native_linux/native_linux_compatibility.html) and the [bitsandbytes installation guide](https://huggingface.co/docs/bitsandbytes/main/en/installation).

The first lesson also names Docker, Git, and CMake as prerequisites but does not provide the same official installation support it gives ROCm/PyTorch. For a course whose nominal prerequisite is basic Python, setup failure is likely to be misdiagnosed as learner failure.

**Remediation:** Choose one honest scope. Either advertise and enforce the exact RX 9070 XT/gfx1201, supported OS/kernel, ROCm/container, host RAM, disk, Docker, Git, CMake, Python, and Ollama matrix, or implement architecture detection and document/test each supported GPU path. Put the complete preflight and resource budget before enrollment or the first irreversible download. Include official installation/readiness links and distinguish supported, experimental, and unsupported combinations.

### H5. Later assessment becomes highly predictable and weakly interleaved

The exercise inventory is substantial—236 exercises across 53 lessons—but quantity masks a repeated pattern:

- all 27 lessons in sections VI–X use the exact sequence `mc`, `text`, `fill`, `write`;
- 49 of 74 multiple-choice questions place the correct answer first;
- 26 of 27 multiple-choice questions in sections VI–X place the correct answer first, including every question in sections VII–X;
- later `write` tasks remain mostly local to the lesson and rarely require retrieval and adaptation of earlier skills.

Learners can exploit position and shape instead of reasoning. Repeated four-item lessons also flatten pacing, and locally cued recall does not prepare learners to diagnose a whole assistant where model identity, retrieval, privacy policy, paths, and serving interact. Several early hints reveal the exact arithmetic or answer rather than a next reasoning step.

**Remediation:** Design an explicit coverage/interleaving grid before rewriting individual exercises. Balance answer positions without a visible cycle; vary assessment types and counts by lesson purpose; revisit earlier memory, privacy, identity, and reproducibility decisions in later contexts; and use error diagnosis, output interpretation, comparison, and transfer tasks. Rewrite hints as graduated prompts that expose one intermediate decision at a time. Re-run distribution and coverage audits after editing.

## Medium findings

### M1. Several Workings promise checks their supplied implementation does not perform

Even apart from answer leakage, some canonical code fails its own brief:

- section I requires proof that llama.cpp is present, but the supplied `doctor.py` does not check it;
- section IV requires source-group grouping, baseline-prompt leakage checks, and rejection reporting, but `curate.py` does not enforce one split per source, scan for baseline leakage, or emit the promised rejection record;
- later evidence often relies on learner-authored reports rather than values derived from the artifact under assessment.

This teaches a damaging habit: a report or rubric assertion appears to count as proof even when the program has not established it.

**Remediation:** For every Working, construct a requirement-to-evidence table and ensure each criterion is produced or checked by the submitted system. Add negative fixtures for missing llama.cpp, cross-source split leakage, baseline prompt leakage, unsafe paths, malformed JSONL, model mismatch, and policy bypass. Remove or reword requirements that cannot be validly observed; do not award them through narrative claims.

### M2. Privacy is taught as inference-time policy more than as an end-to-end data lifecycle

The content handles prompt injection, untrusted retrieved text, source grouping, local binding, and outbox control well. It does not give equally strong treatment to the privacy risks created by imports, caches, logs, debug reports, embeddings, backups, temporary conversion artifacts, grading payloads, model-provider telemetry, or deletion. That omission is particularly visible because the platform's grader itself crosses the promised boundary.

**Remediation:** Add a concise data-flow and threat-model exercise covering ingest, storage, indexing, inference, logs, assessment, retention, backup, and deletion. Require synthetic fixtures for assessment and demonstrate how to inspect network listeners and grader payloads. Make “local” an auditable lifecycle property rather than a label attached only to inference.

### M3. Reading, layout, and wording defects weaken an otherwise strong presentation

Two assigned readings currently return 404:

- the old AMD compatibility URL in `s01/l02`;
- `https://docs.ollama.com/api/version` in `s01/l04`.

The body shape also drifts from authoring guidance:

- `s02/l01` and `s03/l01` each use two callouts despite the one-callout maximum;
- some lessons are visibly over or under the intended prose range;
- `s05/l01` and `s05/l04` contain undocumented `body_words` metadata that does not function as a reliable source of truth;
- “rite” sometimes refers to the overall ten-section arc and sometimes to a lesson or local step;
- the final section refers to “online style references” even though the project intentionally uses local snapshots.

The majority of readings are current, relevant, and well chosen, so this is a repairable consistency issue rather than a wholesale sourcing problem.

**Remediation:** Replace the broken URLs with stable current documentation pages and run a link check over every reading. Normalize callouts and lesson lengths through substantive editing, not metadata counters. Remove undocumented body fields unless the schema adopts them. Reserve “rite” for one stable unit, and describe local snapshots accurately.

### M4. Fixed-total copy and cleanup debt reduce resilience

The boot text says “Ten rites lie ahead.” The configuration guide explicitly warns against fixed numeric totals because the phrase becomes stale when sections are added or reorganized; the nearby `{N}`-based line is the durable pattern. Empty `sections/s11/` and `sections/s12/` directories are not configured and do not affect validation, but they create ambiguity about abandoned or planned content.

Existing identifiers such as `s01-badge` are legacy-shaped rather than a reason to rename them. Renaming stable IDs for cosmetics would risk progress and is not warranted.

**Remediation:** Replace the fixed total with dynamic or nonnumeric language. Remove the two empty orphan directories during the authorized release cleanup if no external process needs them. Preserve existing section, lesson, badge, and exercise IDs wherever their semantic target remains the same; use the chosen migration plan for any unavoidable identity change.

## Important strengths to preserve during reauthoring

- The ten-section arc moves coherently from environment and baseline through memory planning, curation, QLoRA, evaluation, RAG, policy, serving, and rebuild.
- The fictional voice is consistent and generally serves the technical progression rather than obscuring it.
- Every lesson has a field note and at least one reading; every multiple-choice distractor has targeted feedback; non-type exercises consistently have hints.
- The course correctly emphasizes source-group splitting, regex as triage rather than proof, retrieved text as untrusted data, local network binding, and behavioral gates for nondeterministic rebuilds.
- Ten cumulative Workings target one external project, all rubric totals are mechanically valid, and each includes a craft criterion.
- The source attack bank contains 30 challenges—five in every tier—and the generated bank is synchronized. The intrusion pools also have healthy raw depth.
- Four valid themes and a coherent economy/shop configuration give the course strong presentational identity.

These strengths should be carried into the reauthored release, but none offsets the privacy boundary, invalid evidence path, answer-key teaching pattern, or prerequisite failures.
